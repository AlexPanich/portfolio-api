# Portfolio API — цифровая визитка

Backend-приложение, которое через GraphQL API (Apollo Sandbox) рассказывает обо мне: профиль, навыки, опыт работы и проекты.

**Стек:** TypeScript · Node.js 24 · NestJS 12 · GraphQL (Apollo Server 5, code-first) · Prisma 7 · PostgreSQL 18 · Docker · Vitest · GitHub Actions

| | |
|---|---|
| Демо (Apollo Sandbox) | _ссылка появится после деплоя_ |
| Health check | `GET /health` |
| Схема GraphQL | [`schema.gql`](./schema.gql) |

---

## Быстрый старт

Нужен только Docker:

```bash
docker compose up --build
```

Откройте **http://localhost:3000/graphql**: Apollo Sandbox откроется с готовым запросом, останется нажать **Run**.

При старте контейнер сам применяет миграции и заполняет базу (подробнее в разделе [«Инициализация и заполнение БД»](#инициализация-и-заполнение-бд)). Порт базы на хосте — `5434`, чтобы не конфликтовать с локальным PostgreSQL. Порты переопределяются через `DB_PORT` и `API_PORT`.

### Локальная разработка

```bash
cp .env.example .env
docker compose up -d db          # только PostgreSQL
npm install                      # postinstall генерирует Prisma Client
npm run db:migrate               # prisma migrate deploy
npm run db:seed:dev              # заполнить данными
npm run start:dev                # http://localhost:3000/graphql
```

С `LOG_SQL=true` в консоль выводится каждый SQL-запрос, и батчинг DataLoader видно своими глазами.

| Команда | Назначение |
|---|---|
| `npm test` | unit-тесты |
| `npm run test:e2e` | e2e на реальной БД (`portfolio_test`, создаётся автоматически) |
| `npm run lint` / `typecheck` / `format:check` | статический анализ |
| `npm run db:migrate:dev -- --name <name>` | новая миграция |

## API

Запрос из задания работает как есть:

```graphql
query {
  profile {
    name
    description
    skills { name }
    experience { company position }
    projects { name }
  }
}
```

Полная модель:

```graphql
type Query {
  profile(slug: String): Profile        # без slug — профиль по умолчанию; null, если не найден
}

type Profile {
  id, slug, name, headline, description, location
  links: [ProfileLink!]!                # GitHub, LinkedIn, Telegram…  (type: LinkType)
  skills(category: SkillCategory): [Skill!]!
  experience: [Experience!]!            # от новых к старым
  totalExperience: Duration!            # общий стаж, пересекающиеся периоды считаются один раз
  projects: [Project!]!
}

type Experience {
  company, companyUrl, position, location, description
  achievements: [String!]!
  period: Period!                       # startDate, endDate, isCurrent, duration { years months totalMonths }
  technologies: [Skill!]!
}

type Project {
  name, description
  url: URL, repositoryUrl: URL
  technologies: [Skill!]!
}
```

Даты отдаются скаляром `Date` (`YYYY-MM-DD`), ссылки — скаляром `URL` (из `graphql-scalars`), категории навыков и типы ссылок — enum'ами.

## Архитектура

```
src/
├── main.ts                     HTTP-приложение
├── seed.ts                     CLI сидирования (тот же DI-контейнер, без HTTP)
├── config/                     валидация env (zod) + типизированный AppConfig
├── database/                   PrismaService — единственная точка подключения к БД
├── graphql/                    Apollo, контекст запроса, фабрика DataLoader'ов
├── common/                     createGroupedLoader, Clock
├── health/                     /health (проверяет и БД)
├── modules/
│   ├── profile/                Query.profile + поля-связи профиля
│   ├── experience/             period/totalExperience (доменная логика) + technologies
│   ├── projects/               technologies
│   └── skills/                 batch-запросы навыков (в т.ч. через join-таблицы)
└── seed/                       данные резюме, их схема и синхронизация с БД
```

Каждый модуль делится на три слоя с однонаправленными зависимостями:

```
Resolver  ──►  Service  ──►  Repository  ──►  PrismaService
(GraphQL)      (правила)     (запросы)        (подключение)
    │                             ▲
    └──►  DataLoader (на запрос) ─┘
```

- **Resolver** знает только о GraphQL: аргументы, поля, контекст. Бизнес-логики и Prisma в нём нет.
- **Service** содержит бизнес-правила: расчёт периодов и общего стажа, выбор профиля по умолчанию. GraphQL и Prisma ему неизвестны, поэтому логика тестируется без инфраструктуры.
- **Repository** — единственный слой, который пишет запросы к БД. Методы принимают *списки* id и выполняют один запрос, то есть это готовые batch-функции для DataLoader.
- Модели GraphQL (`models/*.model.ts`) отделены от моделей Prisma. Схема API не повторяет схему БД автоматически: например, `period` и `totalExperience` вычисляются, а `profileId` и `position` наружу не отдаются.

Сервис-слой есть только там, где есть логика. Сервис, который просто проксирует вызов в репозиторий, добавляет код без пользы, поэтому у `skills` и `projects` его нет. DataLoader'ы обращаются к репозиториям напрямую: это адаптеры доступа к данным, а не бизнес-логика.

## Обоснование решений

### 1. Вложенные данные: field resolvers + DataLoader

Связи профиля (`links`, `skills`, `experience`, `projects`, `technologies`) реализованы как field resolvers поверх DataLoader.

**Почему не `include` в корневом запросе.** Один большой `include` грузит всё дерево, даже если клиент запросил одно поле `name`. Для этого пришлось бы разбирать `info` (AST запроса) и вручную строить `include`. Получается хрупко и смешивает слои.

**Почему не простые field resolvers.** Тогда `experience { technologies }` порождает классическую проблему N+1: отдельный запрос на каждую позицию.

**Что получилось.** Каждая связь стоит ровно **один SQL-запрос, независимо от количества строк**, и только если её поле реально запрошено:

| Запрос | SQL-запросов |
|---|---|
| `{ profile { name } }` | 1 |
| `{ profile { experience { company } totalExperience { totalMonths } } }` | 2 — `totalExperience` переиспользует загрузку `experience` |
| полный граф (пример в Sandbox) | 7 = профиль + 6 связей |
| тот же граф на профиле с 30 позициями и 30 проектами | **7** |

Эти цифры проверяются в e2e-тестах (`test/profile.e2e-spec.ts`): тест считает реальные SQL-запросы через событие `query` в Prisma.

Детали реализации:

- **Лоадеры создаются на каждый запрос** в `context` Apollo (`LoadersFactory.create()`). Кэш DataLoader не должен жить дольше запроса. Альтернатива — `REQUEST`-scoped провайдеры Nest, но request scope распространяется вверх по всей цепочке зависимостей, и каждый сервис начал бы пересоздаваться на каждый запрос. В нашем варианте все провайдеры остаются синглтонами.
- **`createGroupedLoader`** — один обобщённый хелпер для связей 1:N и M:N. Он раскладывает строки по родительским ключам и сохраняет порядок, заданный в репозитории. Для родителя без связей возвращается `[]`, а не ошибка.
- **M:N через join-таблицу за один запрос.** По умолчанию Prisma грузит связь `ExperienceSkill → Skill` вторым запросом. С `relationLoadStrategy: 'join'` (preview-фича `relationJoins`) получается один `LATERAL JOIN`. Фича в статусе preview, но существует с Prisma 5.8 и широко используется. Если её отключить, ничего не сломается: просто станет 9 запросов вместо 7.
- **Глубина запросов ограничена самой схемой**: в ней нет циклов (у `Skill` нет обратных ссылок на проекты и опыт). Поэтому отдельный лимит глубины или сложности для публичного read-only API не нужен (см. [«Что дальше»](#что-можно-развить-дальше)).

### 2. Модель данных

- **Всё привязано к `Profile`.** Приложение показывает одного человека, но модель от этого не зависит. Второй профиль, например англоязычная версия, добавляется данными, без миграций. Отсюда `profile(slug:)` и `DEFAULT_PROFILE_SLUG`.
- **Навыки нормализованы.** Стек опыта и проектов хранится ссылками на `Skill` через `ExperienceSkill` и `ProjectSkill`, а не свободным текстом. Так у технологии одно каноническое написание, опечатка ловится на этапе сида, а запрос «где я использовал X» — это один `JOIN`.
- **Достижения — `text[]` внутри `Experience`.** Это упорядоченные значения без собственной идентичности, которые всегда читаются вместе с позицией. Отдельная таблица добавила бы JOIN и сущность, которой нечего моделировать.
- **Явный порядок (`position`).** Резюме курируется вручную, поэтому навыки, ссылки и проекты выводятся в авторском порядке. Опыт сортируется по `startDate DESC`.
- **`endDate = NULL` означает текущую работу.** Отдельного флага `isCurrent` в БД нет, чтобы нельзя было получить противоречивые данные. В API `isCurrent` вычисляется.
- **Ограничения и индексы на уровне БД:** enum'ы PostgreSQL (`link_type`, `skill_category`), уникальность (`slug`, `(profile_id, name)`, `(profile_id, url)`), `ON DELETE CASCADE`, индексы под каждую batch-выборку (`profile_id, position`, `profile_id, start_date DESC`) и под обратные связи join-таблиц.
- **UUID v7 как первичные ключи.** Id не перечисляются и не раскрывают число записей, а благодаря монотонности v7 индекс остаётся компактным. Имена в БД в `snake_case` (`@@map` / `@map`), в коде — `camelCase`.

### 3. Бизнес-логика периодов

`period.ts` — чистые функции без зависимостей:

- Резюме оперирует **целыми месяцами**, поэтому обе границы включаются: работа с марта по март — это 1 месяц.
- `totalExperience` **сливает пересекающиеся интервалы** перед суммированием, чтобы параллельная работа (основная плюс контракт) не удваивала стаж.
- Даты читаются в UTC: колонка `DATE` в PostgreSQL приходит как полночь UTC, и локальная таймзона сервера не должна сдвигать месяц.
- «Текущий момент» берётся из инжектируемого `Clock`, поэтому расчёты детерминированы в тестах.

### 4. Инициализация и заполнение БД

Последовательность старта контейнера (`docker-entrypoint.sh`):

```
prisma migrate deploy   →   node dist/seed.js   →   exec node dist/main.js
```

- **Миграции**, а не `db push`: схема версионируется SQL-файлами в `prisma/migrations`, и `migrate deploy` применяет только недостающие под advisory-lock.
- **Данные резюме — типизированный TS-файл** `src/seed/data/profile.data.ts`. Перед записью он проверяется zod-схемой (`seed.schema.ts`): неизвестная технология, перепутанные даты, дубликаты или кривая ссылка останавливают сид с понятным сообщением, и в БД ничего не попадает.
- **Сид работает как синхронизация, а не как «вставка, если пусто».** В одной транзакции профиль удаляется (связи — каскадом) и создаётся заново из файла. Поэтому:
  - операция идемпотентна и безопасно выполняется на каждом старте;
  - в БД всегда ровно то, что в файле, включая *удаления* (upsert удалённое не вычистит);
  - параллельные читатели до коммита видят старую версию (MVCC), а `pg_advisory_xact_lock` сериализует сидеры, если одновременно стартуют несколько реплик.
  - Цена: id пересоздаются при каждом деплое. Для read-only визитки это приемлемо. Если понадобятся стабильные id, их можно детерминированно выводить из естественных ключей (UUID v5).
- **Сид — отдельный процесс** (`NestFactory.createApplicationContext(SeedModule)`), а не хук в `onApplicationBootstrap`. Он переиспользует валидацию конфига и `PrismaService`, но не поднимает HTTP. Ошибка сида роняет деплой до того, как приложение начнёт принимать трафик.
- **`exec`** заменяет shell процессом Node, и тот получает `SIGTERM` напрямую. Вместе с `enableShutdownHooks()` это даёт корректную остановку и закрытие пула соединений.

### 5. GraphQL: code-first

Схема генерируется из TypeScript-классов: один источник правды, типы резолверов и схемы не расходятся. Вне production SDL пишется в `schema.gql`, который лежит в репозитории, поэтому изменения API видны на код-ревью.

Для неизвестного `slug` поле `profile` nullable и возвращает `null` — идиоматичное поведение GraphQL для поиска по ключу, без искусственных ошибок.

**Apollo Sandbox и introspection включены в production осознанно**: это публичная визитка, и Sandbox здесь и есть продукт. CSRF-защита Apollo (`csrfPrevention`) включена по умолчанию, stack trace в ошибках выводится только вне production.

### 6. Конфигурация

Переменные окружения проверяются zod-схемой при старте (`config/env.schema.ts`). Если окружение неверное, приложение не запускается и выводит понятную ошибку, а не падает на первом запросе. Остальной код читает конфиг через типизированный `AppConfig`, а не через строковые ключи.

### 7. Docker

- Multi-stage сборка: в runtime-образ попадают только production-зависимости и скомпилированный `dist`. Процесс работает под пользователем `node`, а не root. Есть `HEALTHCHECK`.
- Слои упорядочены так, что `npm ci` пересобирается только при изменении манифестов или схемы Prisma.
- **Компромисс:** Prisma CLI нужен в runtime для `migrate deploy`, а со своими зависимостями он весит около 250 МБ (образ — около 545 МБ). Альтернатива — отдельный job или контейнер для миграций. Это усложняет деплой и оправдано при нескольких сервисах, но не для одной визитки.

### 8. Тестирование

- **Unit** (`*.spec.ts`): доменная логика периодов (границы, пересечения, UTC), `createGroupedLoader` (батчинг, порядок, пустые группы, ошибки), валидация сида (в том числе реального файла с данными).
- **E2E** (`test/*.e2e-spec.ts`): поднимают настоящее приложение на настоящем PostgreSQL. Проверяют запрос из задания, сортировку, фильтры, `null` для неизвестного slug, **число SQL-запросов** (защита от регресса N+1), идемпотентность сида и отказ записывать невалидные данные, `/health` и Sandbox.
- **CI** (GitHub Actions): формат → линтер → типы → unit → e2e (Postgres как service) → сборка. Отдельный job поднимает `docker compose up` с нуля и делает реальный GraphQL-запрос, то есть проверяет ровно сценарий «запуск с нуля».

### 9. Версии

NestJS 12 распространяется только как ESM, поэтому проект тоже ESM: `"type": "module"`, импорты с `.js`, Vitest вместо Jest. Prisma — последняя стабильная 7.x с новым генератором `prisma-client` и driver adapter `@prisma/adapter-pg`. Prisma 8 на момент написания в RC, поэтому её не беру.

## Деплой (Render + Neon)

- **API** — Docker-сервис на Render, описан в Blueprint [`render.yaml`](./render.yaml): **Dashboard → New → Blueprint → репозиторий**.
- **PostgreSQL** — [Neon](https://neon.tech), бесплатный тариф. Render разрешает одну бесплатную базу на workspace и удаляет её через 30 дней, а Neon бесплатен бессрочно. Регион у обоих — Frankfurt, чтобы между сервисом и базой были минимальные задержки.
- Единственный секрет — `DATABASE_URL`: прямая строка подключения Neon, **не pooled**. `prisma migrate deploy` использует session-level advisory lock, а transaction-пулер его ломает.
- Миграции и сид выполняются при каждом старте контейнера, поэтому деплой сводится к push в `main`.

На бесплатном тарифе Render сервис засыпает после 15 минут без запросов, поэтому первый запрос после простоя занимает около 30–60 секунд. База Neon тоже засыпает и просыпается примерно за секунду.

## Что можно развить дальше

- Мутации для редактирования резюме: аутентификация (`@nestjs/authentication`), DTO с валидацией, отказ от «сид как источник правды» в пользу админки.
- Хранение аватара или PDF-резюме в S3-совместимом хранилище (MinIO локально), с presigned URL в API.
- Ограничение сложности запросов и persisted queries, если схема обрастёт циклическими связями.
- HTTP-кэширование (`@cacheControl` + CDN): данные меняются только при деплое.
- Наблюдаемость: структурированные логи, трейсинг резолверов.
